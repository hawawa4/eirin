# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This project is a Golang project that aims to create a simple but powerful library manager for astrophotography.
The project uses Go for the backend part, which in turn will use Siril for the ACTUAL astro processing, with Wails as a bridge to use Svelte for the frontend display part.
The Svelte frontend uses typescript with prettier and eslint.

The main features of the application are:

- Multiplatform
- Local, classic desktop app, no webserver
- "NAS first" approach: Your astrophotography data lives in the NAS, you handle Siril projects through symlinks on local folders
- Copy data from the Seestar onto the NAS without duplicating files (own copy logic in `internal/importer`, skips files already in the library)
- Preview autostretched FITS and delete them from the NAS/project
- Automatically handle sequence creation and management, offloading the processing to siril via cli

## Development notes

Do not put all the code into one file. Prefer a cleaner approach.

## Tool notes

Don't try and find the go binary in path. Only use the `just` commands to interact with the go binary. In general, prefer using the `just` commands over messing with "find stuff on path or other user folders".

## Commands

All development goes through `just` (see `Justfile`):

- `just dev` — live-reload dev mode (`wails3 dev`); Go recompiles on save, Vite handles Svelte HMR
- `just build` — production binary via `wails3 build`, output in `build/bin/`
- `just build-backend` — `go build ./` only (no frontend/wails packaging)
- `just build-frontend` — `npm run build` in `frontend/` only
- `just build-server` — headless server binary (`go build -tags server`), output `eirin-server`
- `just test` — `go test ./internal/...` (all Go unit tests)
- `just test-server` — the same tests against the headless build (`-tags server`); CI runs both
- `just check` — type-check only: `go build ./...` + `npm run check` (svelte-check + tsc) in `frontend/`
- `just lint` — `staticcheck ./...` + frontend ESLint/Prettier check
- `just format` — Prettier write on `frontend/`
- `just install-frontend` / `just install-backend` — install npm deps / `go mod tidy`
- `just landing-dev` / `just landing-build` / `just landing-check` / `just landing-docker` / `just install-landing` — the landing page (see below)

To run a single Go test: `go test ./internal/store/... -run TestName` (or scope to any package path). `just test` only covers `internal/...`, not the root package.

The Justfile pins `PATH` to include `~/go/bin` and `/usr/local/go/bin` — Go tools and the Wails CLI (`wails3`) must be installed there (`go install .../wails/v3/cmd/wails3@...`, `go install honnef.co/go/tools/cmd/staticcheck@latest`).

Note: the project runs on **Wails v3** (`wails3` CLI, `github.com/wailsapp/wails/v3`), not v2 — `main.go` uses the v3 `application.New` / `application.Service` API.

## Architecture

Backend is written in Go, split by responsibility under `internal/`:

```
internal/
  app/         — Wails service/handlers only (*App methods, event emission, dialogs)
  catalog/     — star catalog, annotations, moon phase math
  fits/        — FITS parsing, pixel processing, previews
  importer/    — file scanning and copy logic
  indexer/     — FITS file detection helper
  server/      — HTTP API server
  siril/       — Siril detection, execution, output parsing
  snapshot/    — library snapshot: desktop Publisher, server Loader
  store/       — SQLite DB, frames, projects, prefs
```

`internal/app` is the largest package by far and is where Wails-bound methods live; it wires together `store`, `importer`, `indexer`, `siril`, and `fits`. Keep new cross-cutting logic in its own package rather than growing `app` further — `app` should stay thin glue over the other packages.

Frontend is Svelte + TypeScript under `frontend/`, using Wails-autogenerated bindings in `frontend/wailsjs/` — do not hand-edit generated bindings, they're regenerated by the Wails build.

### Data flow / domain model

- All astrophotography data (subs, calibration frames, stacked/processed frames) lives in a user-designated root folder, intended to be a NAS mount. Eirin catalogs it into SQLite (`internal/store`) rather than duplicating files.
- Import: copies data from a Seestar device onto the root folder (`internal/importer`), skipping files already in the library; optional delete-from-source only after a full SHA-256 match.
- Projects: Siril processing projects are built as local folders symlinked back to NAS-resident frames (not copies), then handed to Siril via CLI (`internal/siril`) for stacking/processing.
- FITS files are parsed and rendered as autostretched preview PNGs (`internal/fits`); users can inspect and delete bad frames directly against the NAS/project.

### Persistence & environment overrides

- SQLite prefs/catalog DB defaults to the platform config dir (`~/.config/eirin/prefs.db` on Linux, etc.) — overridable via `EIRIN_DB_PATH`.
- Wails' local webserver port is overridable via `EIRIN_PORT`.
- Tests must never touch the real user DB: every package with DB-dependent tests sets `EIRIN_DB_PATH` to a temp path in its `TestMain` (`main_test.go`).

### Testing conventions

- Tests are whitebox (same package as the code under test), one `_test.go` file per source file.
- `newTestStore(t)` / `newTestApp(t)` helpers (in each package's `main_test.go`) build isolated store/app instances backed by a `t.TempDir()` SQLite file — never in-memory, never the real DB.

### Headless/server mode

`just build-server` builds a `-tags server` binary for headless Docker deployment: a strictly read-only viewer of final images (stacked/processed/image types) plus the Sky Atlas. It embeds `frontend/dist`, so run `just build-frontend` first. `just docker-build` builds the image via the root `Dockerfile` (multi-stage: Node frontend build → Go backend build with `CGO_ENABLED=0` → minimal `alpine` runtime; the binary is fully static since `modernc.org/sqlite` is pure Go).

The server never shares the desktop's database. The desktop's `snapshot.Publisher` (enabled by the `snapshot_enabled` pref, Settings → Server viewer) writes a `VACUUM INTO` copy to `<root>/.eirin/library.db` after changes and on shutdown. The server's `snapshot.Loader` polls it, copies it to `EIRIN_DB_PATH`, rewrites `nas_path` prefixes to `EIRIN_ROOT` (required env var), prunes it to non-rejected final images, and swaps it in read-only (`App.db` is an `atomic.Pointer`; always use `a.store()`), emitting `library:updated`. Startup is split in `startup_desktop.go`/`startup_server.go`.

Read-only is enforced in the backend, not just the UI: every method that writes to the DB or the filesystem starts with `a.requireWritable()` (returns `errReadOnly` in server builds), and path-taking reads (previews, headers, raster images, atlas sizes, `/api/image`, directory listings) call `a.checkServable(path)`, which only allows paths in the viewer's `frames` table. Add both guards to any new method of those kinds. Tests of write methods call `skipInServer(t)`. Methods that can't work headlessly at all (Siril, Seestar import, reveal in file manager) are still split into `_desktop.go`/`_server.go` pairs gated by `//go:build !server` / `//go:build server`.

`internal/app/capabilities.go` exposes `AppInfo.Capabilities.DesktopMode` and `.ReadOnly` to the frontend. In read-only mode it shows only the Library (`components/viewer/ViewerLibrary.svelte`, not `LibraryView`; its `PreviewPane` runs with `serverRendered`, fetching ~1 MB JPEGs from `GetViewerPreview` instead of tens of MB of raw float pixels over the network — the Sky Atlas deliberately keeps its raw-pixel previews), Sky Atlas and Settings tabs, and `lib/prefs.ts` keeps preferences in the browser's `localStorage` instead of `SetPref`; always persist prefs through `savePref`.

Two independent HTTP listeners run in server mode: Wails' own server (serves the Svelte frontend + RPC/WebSocket events, via `WAILS_SERVER_HOST`/`WAILS_SERVER_PORT`) and Eirin's pre-existing side-channel REST API (`internal/server`, `/api/status` `/api/frames` `/api/image`, via `EIRIN_PORT`) — don't conflate the two when changing ports.

### Landing page

`landingpage/` is a separate, fully static [Astro](https://astro.build) site (its own `package.json`, not part of the Wails build), served by nginx from a Docker image (`landingpage/Dockerfile`, built from the repo root, port 8080) that `.github/workflows/landingpage.yml` pushes to `ghcr.io/hawawa4/eirin-landingpage` on pushes to `main`; the owner hosts it at https://eirin.hawawa.org. Screenshots are imported straight from `../docs/img/`, shared with the README, so retaking a screenshot there updates both. Short `.webm` clips in `../docs/vid/` (imported with `?url`) are shown by `VideoShot.astro`: the screenshot is the poster, and the clip only loads and plays once scrolled into view (never autoplays under `prefers-reduced-motion`). `site`/`base` in `astro.config.mjs` default to `https://eirin.hawawa.org` + `/` and can be overridden with `SITE_URL`/`BASE_PATH` (also Docker build args). Keep the copy plain and factual; no AI-generated images.

### Linux note

Wails requires `libwebkit2gtk-4.1-dev` (not the older 4.0 variant) on Ubuntu 22.04+/derivatives. Wails v3 defaults to GTK4/webkitgtk-6.0 on Linux since alpha.93; this project targets the GTK3/webkit2gtk-4.1 stack instead, so `build/linux/Taskfile.yml` passes `-tags gtk3` to `go build` (and `wails3 generate bindings`). The `wails3` CLI itself must also be installed with `-tags gtk3` (`go install -tags gtk3 github.com/wailsapp/wails/v3/cmd/wails3@...`), or its own cgo-linked internals will probe for GTK4/webkitgtk-6.0 instead.
