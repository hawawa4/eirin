# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This project is a Golang project that aims to create a simple but powerful library manager for astrophotography.
The project uses Go for the backend part, which in turn will use Siril for the ACTUAL astro processing, with Wails as a bridge to use Svelte for the frontend display part.
The Svelte frontend uses typescript with prettier and eslint.

The main features of the application are:

- Multiplatform
- Local, classic desktop app, no webserver
- "NAS first" approach: Your astrophotography data lives in the NAS, you handle Siril projects through symlinks on local folders
- Copy data from the Seestar onto the NAS without duplicating files (own copy logic in `internal/importer`, skips files already in the library)
- Preview autostretched FITS and delete them from the NAS/project
- Automatically handle sequence creation and management, offloading the processing to siril via cli

## Development notes

Do not put all the code into one file. Prefer a cleaner approach.

## Tool notes

Don't try and find the go binary in path. Only use the `just` commands to interact with the go binary. In general, prefer using the `just` commands over messing with "find stuff on path or other user folders".

## Commands

All development goes through `just` (see `Justfile`):

- `just dev` — live-reload dev mode (`wails3 dev`); Go recompiles on save, Vite handles Svelte HMR
- `just build` — production binary via `wails3 build`, output in `build/bin/`
- `just build-backend` — `go build ./` only (no frontend/wails packaging)
- `just build-frontend` — `npm run build` in `frontend/` only
- `just build-gallery` — `npm run build:gallery` in `frontend/` (the public gallery's frontend, into `frontend/dist-gallery`)
- `just build-server` — headless server binary (`go build -tags server`), output `eirin-server`; run `just build-gallery` first
- `just test` — `go test ./internal/...` (all Go unit tests)
- `just test-server` — the same tests against the headless build (`-tags server`); CI runs both
- `just check` — type-check only: `go build ./...` + `npm run check` (svelte-check + tsc) in `frontend/`
- `just lint` — `staticcheck ./...` + frontend ESLint/Prettier check
- `just format` — Prettier write on `frontend/`
- `just install-frontend` / `just install-backend` — install npm deps / `go mod tidy`
- `just landing-dev` / `just landing-build` / `just landing-check` / `just landing-docker` / `just install-landing` — the landing page (see below)

To run a single Go test: `go test ./internal/store/... -run TestName` (or scope to any package path). `just test` only covers `internal/...`, not the root package.

The Justfile pins `PATH` to include `~/go/bin` and `/usr/local/go/bin` — Go tools and the Wails CLI (`wails3`) must be installed there (`go install .../wails/v3/cmd/wails3@...`, `go install honnef.co/go/tools/cmd/staticcheck@latest`).

Note: the project runs on **Wails v3** (`wails3` CLI, `github.com/wailsapp/wails/v3`), not v2 — `main.go` uses the v3 `application.New` / `application.Service` API.

## Architecture

Backend is written in Go, split by responsibility under `internal/`:

```
internal/
  app/         — Wails service/handlers only (*App methods, event emission, dialogs)
  catalog/     — star catalog, annotations, moon phase math
  fits/        — FITS parsing, pixel processing, previews
  importer/    — file scanning and copy logic
  indexer/     — FITS file detection helper
  gallery/     — public gallery (server build) pure logic: config, opaque ids, file-name metadata
  server/      — HTTP API server (desktop only)
  siril/       — Siril detection, execution, output parsing
  snapshot/    — library snapshot: desktop Publisher, server Loader
  store/       — SQLite DB, frames, projects, prefs
  updater/     — GitHub-release update check + in-place install
```

`internal/app` is the largest package by far and is where Wails-bound methods live; it wires together `store`, `importer`, `indexer`, `siril`, and `fits`. Keep new cross-cutting logic in its own package rather than growing `app` further — `app` should stay thin glue over the other packages.

Frontend is Svelte + TypeScript under `frontend/`, using Wails-autogenerated bindings in `frontend/wailsjs/` — do not hand-edit generated bindings, they're regenerated by the Wails build.

### Data flow / domain model

- All astrophotography data (subs, calibration frames, stacked/processed frames) lives in a user-designated root folder, intended to be a NAS mount. Eirin catalogs it into SQLite (`internal/store`) rather than duplicating files.
- Import: copies data from a Seestar device onto the root folder (`internal/importer`), skipping files already in the library; optional delete-from-source only after a full SHA-256 match.
- Projects: Siril processing projects are built as local folders symlinked back to NAS-resident frames (not copies), then handed to Siril via CLI (`internal/siril`) for stacking/processing.
- FITS files are parsed and rendered as autostretched preview PNGs (`internal/fits`); users can inspect and delete bad frames directly against the NAS/project.

### Persistence & environment overrides

- SQLite prefs/catalog DB defaults to the platform config dir (`~/.config/eirin/prefs.db` on Linux, etc.) — overridable via `EIRIN_DB_PATH`.
- Wails' local webserver port is overridable via `EIRIN_PORT`.
- Tests must never touch the real user DB: every package with DB-dependent tests sets `EIRIN_DB_PATH` to a temp path in its `TestMain` (`main_test.go`).

### Testing conventions

- Tests are whitebox (same package as the code under test), one `_test.go` file per source file.
- `newTestStore(t)` / `newTestApp(t)` helpers (in each package's `main_test.go`) build isolated store/app instances backed by a `t.TempDir()` SQLite file — never in-memory, never the real DB.

### Headless/server mode: the public gallery

`just build-server` builds a `-tags server` binary for headless Docker deployment: a **public photo gallery** (grid + lightbox, Sky Atlas, Slideshow) of the final images (processed/image types) that the user marked **public** (`frames.public`, set from the Library with `App.SetFilesPublic`: Public button, `p`, context menu). It is a different program from the desktop app, not the app in read-only mode:

- `main_server.go` binds only `app.Gallery` (`internal/app/gallery_server.go`) to Wails, never `*App`, so no library RPC exists on the server; `main_desktop.go` binds `*App`. `Gallery.ServiceStartup/Shutdown` run `App`'s lifecycle. The side-channel REST API and `/eirin/raw` are off in the server build.
- Visitors address pictures by opaque ids (`gallery.PublicPath`: `/g/<sha256 prefix>.<ext>`), never by path or file name. `GalleryInfo` carries only title/texts and, per picture, an id, title, and details parsed server-side from the file name (`gallery.Describe`, a port of `lib/slideshow/frameInfo.ts`). `servePreview` resolves ids with `a.publicToReal` and refuses anything else. Never return a path, file name or non-final frame from `Gallery`.
- Config (`gallery.Load`): `EIRIN_GALLERY_*` env vars over an optional JSON file (`/data/gallery.json` or `EIRIN_GALLERY_CONFIG`): title, subtitle, about, theme, default view, format, home link. No settings UI.
- The frontend is its own bundle: entry `frontend/gallery/`, app in `frontend/src/gallery/`, built by `vite.gallery.config.ts` into `frontend/dist-gallery` (embedded only by the server build; the desktop embeds `frontend/dist`). It reuses `SkyAtlas.svelte` and `SlideshowView.svelte` with a `gallery` prop (no file names, no format switch, no desktop actions). Their `$app` imports are aliased to `src/gallery/appShim.ts`, which answers the same calls from `Gallery` (called by name, `Call.ByName`: there are no generated bindings for it) — anything the shared code imports from `$app` must exist there. Routing is by URL hash (`#/atlas`, `#/slideshow`, `#/image/<id>`).
- Format: the library often holds a picture twice (processed FITS + PNG/JPEG export). `gallery.ChooseFormat` picks one set for the grid and slideshow (`auto` = exports if any); the Atlas gets the plate-solved ones of that set, else the plate-solved FITS.

`just docker-build` builds the image via the root `Dockerfile` (multi-stage: `npm run build:gallery` → Go backend build with `CGO_ENABLED=0` → minimal `alpine` runtime; the binary is fully static since `modernc.org/sqlite` is pure Go).

The server never shares the desktop's database. The desktop's `snapshot.Publisher` (enabled by the `snapshot_enabled` pref, Settings → Server viewer) writes a `VACUUM INTO` copy to `<root>/.eirin/library.db` after changes and on shutdown. The server's `snapshot.Loader` polls it, copies it to `EIRIN_DB_PATH`, rewrites `nas_path` prefixes to `EIRIN_ROOT` (required env var), prunes it to non-rejected final images marked public (`PruneToFinals`; `buildGallery` checks the flag again), and swaps it in read-only (`App.db` is an `atomic.Pointer`; always use `a.store()`), emitting `library:updated`. Startup is split in `startup_desktop.go`/`startup_server.go`.

As defence in depth (`*App` isn't even bound in server builds): every `App` method that writes to the DB or the filesystem starts with `a.requireWritable()` (returns `errReadOnly` in server builds), and path-taking reads (previews, headers, raster images, atlas sizes, `/api/image`, directory listings) call `a.checkServable(path)`, which only allows paths in the viewer's `frames` table. Add both guards to any new method of those kinds. Tests of write methods call `skipInServer(t)`. Methods that can't work headlessly at all (Siril, Seestar import, reveal in file manager) are still split into `_desktop.go`/`_server.go` pairs gated by `//go:build !server` / `//go:build server`.

`internal/app/capabilities.go` exposes `AppInfo.Capabilities.DesktopMode` and `.ReadOnly` to the desktop frontend (always desktop/writable there now, since the server serves the gallery bundle instead). In the gallery `lib/prefs.ts` keeps preferences in the browser's `localStorage` instead of `SetPref`; always persist prefs through `savePref`. (`PreviewPane`'s `serverRendered` option, from the old read-only Library viewer, is currently unused.)

### Display images (Sky Atlas, Slideshow, public gallery)

Anything shown as a finished picture goes through `internal/previews`, served as plain JPEGs on `GET /eirin/preview?path=&size=&stretch=` (`app.PreviewRoute`). That route is mounted on Wails' own asset server via `app.AssetMiddleware` (`AssetOptions.Middleware` in `main.go`), so it is same-origin in both builds and images never travel as base64 inside RPC replies. Don't add RPC methods that return image data; use this route. Each file version is rendered once at native size (capped at `fits.MaxRenderSize`) and shrunk into a pyramid of levels (`previews.Levels`: 512/1024/2048/4096, plus native), cached on disk (`EIRIN_CACHE_DIR`, `EIRIN_PREVIEW_CACHE_MB`) and in a memory LRU. Concurrent requests share one render, and renders are bounded (`renderSlots`). Responses carry an ETag and `no-cache`, so browsers revalidate cheaply (304). The frontend (`lib/images.ts`) asks for the level matching the on-screen size × devicePixelRatio and asks again as the user zooms: the Atlas per overlaid footprint (`lib/atlas/previews.ts`), the Slideshow per area size, and `PreviewPane` per zoom. The server pre-renders the gallery's pictures after each snapshot (`warmPreviews`, `EIRIN_PREVIEW_WARM=0` to disable), stopping at 80% of the cache budget. The desktop Library's FITS preview stretches pixels itself (adjustable stretch, histogram, WebGL): it fetches them from `GET /eirin/raw?path=&size=` (`app.RawPreviewRoute`, `fits.EncodeRawPreview`: a JSON header including the FITS header, then uint16 samples), not an RPC; `lib/library/previewCache.ts` aborts loads for rows the user moved past, and the backend drops requests whose client went away while waiting for a render slot. Blink still uses `GeneratePreview`.

The Sky Atlas is the landing view. Once it has loaded and painted (`onready`), App mounts the Library hidden so it loads in the background, then (desktop) Coverage once the Library has loaded (`onloaded`) — see "Background preloading" in `App.svelte`. Views mounted while hidden must cope with a 0×0 size and `active=false` until shown.

`fits.ReadFITSHeader` reads only the header blocks (fitsio's own `Open` reads every HDU's data), and pixels are streamed straight into float32 (`fits/reader.go`). Keep header-only callers off any path that loads pixels.

The server build has one HTTP listener: Wails' own server (the gallery frontend + RPC/WebSocket events, via `WAILS_SERVER_HOST`/`WAILS_SERVER_PORT`). Eirin's side-channel REST API (`internal/server`, `/api/status` `/api/frames` `/api/image`, via `EIRIN_PORT`) is desktop-only — don't conflate the two when changing ports.

### Updates

Settings → Updates (desktop only, `components/settings/UpdatesSection.svelte`) checks `releases/latest` on GitHub **only when the user clicks "Check for updates"** — never at startup or in the background. `internal/updater` is pure Go; `internal/app/updates_desktop.go` is the thin Wails layer (`CheckForUpdate`, `InstallUpdate`, `RestartApp`, `OpenReleasePage`; `_server.go` stubs). The running version is `updater.Current`, injected via `-ldflags -X` from the `EIRIN_VERSION` env var in `build/linux/Taskfile.yml` (`release.yml` sets it to the tag; anything else is `"dev"` and is never updated). How it installs depends on `updater.Detect()`: AppImage (`$APPIMAGE`) and bare binary (zip) are replaced atomically in place; a `.deb` (exe under `/usr/`, not `/usr/local/`) is downloaded and installed with `pkexec apt-get install` (polkit password dialog, since a GUI has no tty for sudo). Every download is verified against the release's `SHA256SUMS` (written by the `release` job) and refused without one. Release asset names (`eirin-linux-amd64.{AppImage,deb,zip}`) are what the updater looks for — keep them in sync with `release.yml`.

### Landing page

`landingpage/` is a separate, fully static [Astro](https://astro.build) site (its own `package.json`, not part of the Wails build), served by nginx from a Docker image (`landingpage/Dockerfile`, built from the repo root, port 8080) that `.github/workflows/landingpage.yml` pushes to `ghcr.io/hawawa4/eirin-landingpage` on pushes to `main`; the owner hosts it at https://eirin.hawawa.org. Screenshots are imported straight from `../docs/img/`, shared with the README, so retaking a screenshot there updates both. Short `.webm` clips in `../docs/vid/` (imported with `?url`) are shown by `Media.astro`: the screenshot is the poster, and the clip only loads and plays once scrolled into view (never autoplays under `prefers-reduced-motion`). `site`/`base` in `astro.config.mjs` default to `https://eirin.hawawa.org` + `/` and can be overridden with `SITE_URL`/`BASE_PATH` (also Docker build args). Keep the copy plain and factual; no AI-generated images.

### Linux note

Wails requires `libwebkit2gtk-4.1-dev` (not the older 4.0 variant) on Ubuntu 22.04+/derivatives. Wails v3 defaults to GTK4/webkitgtk-6.0 on Linux since alpha.93; this project targets the GTK3/webkit2gtk-4.1 stack instead, so `build/linux/Taskfile.yml` passes `-tags gtk3` to `go build` (and `wails3 generate bindings`). The `wails3` CLI itself must also be installed with `-tags gtk3` (`go install -tags gtk3 github.com/wailsapp/wails/v3/cmd/wails3@...`), or its own cgo-linked internals will probe for GTK4/webkitgtk-6.0 instead.
